# 🧬 `01 // WHAT IS SITEFORGE?`

**SiteForge is an AI-powered business-to-website engineering pipeline.**

It transforms raw business information into:

```text
BUSINESS DATA
      ↓
BUSINESS INTELLIGENCE
      ↓
BRAND DNA
      ↓
WEBSITE STRATEGY
      ↓
LANDING PAGE SPECIFICATION
      ↓
VALIDATION
      ↓
WEBSITE GENERATION
      ↓
DEPLOYABLE WEBSITE
```

SiteForge is deliberately **not** designed as:

```text
PROMPT
  ↓
LLM
  ↓
RANDOM HTML
```

Instead, AI operates inside a controlled software architecture where generated information passes through explicit contracts, validation boundaries, normalization, testing, and isolation.

The result is a system designed around a simple engineering principle:

```text
PROBABILISTIC AI
       +
DETERMINISTIC SOFTWARE
       +
EXPLICIT CONTRACTS
       =
RELIABLE GENERATION PIPELINE
```

# 🧠 `02 // THE PROBLEM`

Traditional AI website generation often collapses an entire problem into one prompt.

That creates several failure modes:

```text
INCOMPLETE DATA
       ↓
AI GUESSING
       ↓
HALLUCINATED BUSINESS INFORMATION
       ↓
INCORRECT WEBSITE
```

Or:

```text
BUSINESS A
       ↓
AI CONTEXT
       ↓
BUSINESS B
       ↓
STATE CONTAMINATION
       ↓
BUSINESS A CONTENT APPEARS ON B
```

Or:

```text
AI RESPONSE
       ↓
MALFORMED JSON
       ↓
PARSER FAILURE
       ↓
PIPELINE COLLAPSE
```

SiteForge treats these as **engineering problems**, not merely prompting problems.


Example:

```json

  "category": "Furniture Store",
  "coordinates": {
    "lat": 30.9003452,
    "lng": 75.85667325
  },
  "address": null,
  "phone": null,
  "website": null,
  "rating": null,
  "reviewCount": null
}
```

The engineering objective is:

```text
MESSY EXTERNAL INFORMATION
             ↓
NORMALIZED INTERNAL REPRESENTATION
```

External information can be:

- incomplete
- missing
- ambiguous
- malformed
- unavailable
- inconsistent

The extraction service therefore creates a controlled boundary between external data and internal application state.

```text
    ≠

```

even when both pass through the same service instances and AI providers.

# 🔐 `06 // STATE ISOLATION`

One of the most important correctness properties in the system is **business isolation**.

SiteForge explicitly tests sequences such as:

```text
A → B → A → C
```

Expected behavior:

```text
A1 === A2

A ≠ B
A ≠ C
B ≠ C
```

Example verification:

```text
╔══════════════════════════════════════════════════╗
║              ISOLATION VERIFICATION             ║
╠══════════════════════════════════════════════════╣
║                                                  ║
║  Place ID isolation ................. PASS      ║
║  Business name isolation ............ PASS      ║
║                                                  ║
║  Sequence: A → B → A → C                         ║
║  Cross-business contamination ...... NONE       ║
║                                                  ║
╚══════════════════════════════════════════════════╝
```

This prevents:

```text
REQUEST A
   ↓
Business A
   ↓
REQUEST B
   ↓
Business B
   ↓
Business A STATE LEAK
```

from silently producing a plausible but incorrect website.

```text
   ↓

   ↓
```

Example:




# 🧩 `12 // LANDING PAGE CONTRACT`

A JSON response is not considered valid merely because it parses.

The structure itself must satisfy application requirements.

Example:

```text
navigation
hero
trustIndicators
services
valueProposition
about
faq
location
cta
footer
```

The specification stores these as:

```js
spec.sections[]
```

Therefore a hero section is located structurally:

```js
const hero = spec.sections.find(
  section => section.type === "hero"
);
```

rather than assuming:

```js
spec.hero
```

This separation between **data representation** and **consumer expectations** is a critical engineering boundary.

```text

 ↓

 ↓
```


Not:

```text

 ↓
```

```text
                          │
                          ▼
                ┌───────────────────┐
                │ AI ABSTRACTION    │
                └─────────┬─────────┘
                          │
```

# 🧠 `23 // ENGINEERING PRINCIPLES`

## `Separation of Concerns`

Business extraction should not be responsible for UI generation.

```text
DATA ≠ STRATEGY ≠ UI
```

## `Single Responsibility`

Each service should have one primary job.

## `Explicit Contracts`

Services should communicate through predictable structures.

## `Fail Fast`

Invalid data should not silently propagate.

## `Defensive Parsing`

AI responses should be considered untrusted.

## `State Isolation`

One business must not contaminate another.

## `Observability`

Failures must be diagnosable.

## `Testability`

Critical pipeline boundaries must be independently testable.

## `Provider Independence`

Core application logic should not depend unnecessarily on one AI provider.

# 🧪 `24 // DEBUGGING PHILOSOPHY`

When the pipeline fails:

```text
DO NOT PATCH THE SYMPTOM FIRST.
```

Instead:

```text
1. IDENTIFY THE BOUNDARY
2. INSPECT THE INPUT
3. INSPECT THE OUTPUT
4. VERIFY THE CONTRACT
5. VERIFY STATE
6. REPRODUCE THE FAILURE
7. FIX THE ROOT CAUSE
8. ADD A REGRESSION TEST
```

Example:

```text
Missing "navigation"
        ↓
Do not immediately modify validator
        ↓
Inspect AI output
        ↓
Check section structure
        ↓
Check normalization
        ↓
Check service contract
        ↓
Determine actual failure boundary
        ↓
Fix
        ↓
Regression test
```
